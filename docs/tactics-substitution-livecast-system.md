# 战术、换人、文字直播联动系统策划案

## 1. 背景问题

当前游戏已经具备三个看起来成立的模块：

- 战术系统：玩家可以切换进攻、防守策略，并产生数值影响。
- 换人系统：玩家可以在暂停或节间调整阵容，管理体力和状态。
- 文字直播系统：每个回合会生成比赛叙事，呈现得分、失误、封盖、犯规等事件。

但玩家反馈是：这三者“看起来都挺好”，实际玩起来却没有明显的环环相扣感。

核心问题不是系统数量不够，而是三者之间缺少共同的因果结构。现在的体验更像：

```text
战术按钮 -> 改概率
换人按钮 -> 改体力 / 阵容
文字直播 -> 播结果
```

目标体验应该是：

```text
场上问题出现 -> 玩家判断战术 -> 换人支持战术 -> 回合产生结果 -> 文字直播解释原因 -> 对手再调整
```

也就是说，玩家需要感受到自己不是在点击孤立功能，而是在读局、布置、承担后果。

## 2. 设计目标

本次系统设计的目标是让战术、换人、文字直播成为同一套“教练决策系统”。

玩家每次操作都应该回答三个问题：

- 我为什么要切这个战术？
- 我为什么要换这个人？
- 刚才这几个回合为什么变好了，或者为什么没变好？

系统侧则要做到：

- 战术有明确适用条件，而不只是概率加成。
- 换人有明确战术目的，而不只是体力替换。
- 文字直播能解释战术和阵容带来的因果，而不只是播报结果。
- 对手会根据玩家倾向做出反制，迫使玩家继续调整。

最终玩家体验应该从“点按钮看结果”变成“读局势做调整”。

## 3. 核心玩法循环

新的主循环定义为：

```text
观察局势
识别问题
选择战术
匹配阵容
观察 3-5 回合反馈
继续调整
```

这一循环要在比赛中不断出现。

典型流程：

```text
1. 对手联防收缩，我方连续冲框失败。
2. 玩家识别：需要外线惩罚联防。
3. 玩家切换“外线火力”。
4. 系统检查：当前阵容空间是否足够。
5. 如果空间不足，文字直播反馈“思路对，但阵容执行不了”。
6. 玩家暂停，换上射手。
7. 接下来几个回合，系统反馈“换人让战术开始见效”。
8. 对手开始扑外线，玩家需要再变招。
```

这个循环的重点不是一次操作立即给奖励，而是让操作进入后续回合，形成持续反馈。

## 4. 新核心层：回合因果上下文

建议新增一个中间层：`PossessionContext`。

它在每个回合开始或结算时生成，用来记录这回合为什么会这样。

示例结构：

```js
{
  possessionId: 42,
  offenseTeam: "knicks",
  defenseTeam: "spurs",
  offScheme: "perimeter",
  defScheme: "zone",
  matchupResult: "offense_advantage",
  lineupFit: "good_spacing",
  fatigueRisk: "primary_handler_tired",
  hotPlayer: "bridges",
  coldPlayer: "brunson",
  primaryCause: "zone_gives_corner_three",
  secondaryCause: "bench_shooter_added_spacing",
  outcomeTags: ["open_three", "weakside_creation", "made"],
  coachRelevant: true
}
```

`PossessionContext` 不是单纯为了调数值，而是为了统一三套系统：

- 战术系统负责提供 `offScheme`、`defScheme`、`matchupResult`。
- 换人系统负责提供 `lineupFit`、`fatigueRisk`、球员标签。
- 文字直播系统读取 `primaryCause`、`secondaryCause`、`outcomeTags` 来生成解释性文本。
- 教练反馈系统根据连续几个 `PossessionContext` 判断调整是否奏效。

## 5. 战术系统改造

### 5.1 战术不再只是数值修正

每套战术都应该拥有四类信息：

```text
克制对象
执行需求
主要收益
失败风险
```

例如：

```text
外线火力
克制：联防、收缩护框
执行需求：至少 2 个稳定外线点，最好有一个持球分球点
主要收益：提升三分机会，拉开禁区空间
失败风险：被换防一体压制，或因持球点体力不足导致出球慢
```

```text
巨星单打
克制：人盯人、防守弱点明显时
执行需求：核心体力、手感、单打能力
主要收益：稳定制造出手或犯规
失败风险：被包夹核心时容易失误，体力消耗大
```

```text
团队传导
克制：包夹核心、慢速收缩防守
执行需求：多个传球点、空间、稳定终结点
主要收益：提高助攻和空位机会
失败风险：被全场紧逼打乱节奏
```

防守战术也同样定义：

```text
全场紧逼
克制：团队传导、慢速阵地、单持球点阵容
执行需求：外线防守、体力、替补深度
主要收益：提高失误，制造快攻
失败风险：体力消耗大，被快速推进后身后空虚
```

```text
包夹核心
克制：巨星单打、核心持球过重
执行需求：轮转、防守纪律
主要收益：压低核心效率，提高失误
失败风险：弱侧射手被放空
```

### 5.2 战术结算增加“执行质量”

战术不应该只看：

```text
进攻战术 vs 防守战术
```

还要看：

```text
这套阵容能不能执行这个战术
```

所以每回合战术收益可以拆成：

```text
战术克制分
阵容适配分
状态执行分
对手反制分
```

示例：

```text
外线火力 vs 联防：战术克制 + 高
阵容空间不足：阵容适配 - 中
主控体力低：状态执行 - 低
最终结果：思路正确，但效果打折
```

这会自然产生更有解释力的文字：

```text
尼克斯这次思路是对的，想用外线惩罚联防；但场上空间点不够，马刺还是敢继续收在禁区。
```

## 6. 换人系统改造

### 6.1 换人从体力管理升级为战术资源管理

当前换人主要解决：

```text
谁累了
谁状态不好
谁该轮换
```

未来换人还要解决：

```text
我要执行什么战术，需要什么球员
对手正在用什么战术，我需要什么球员破解
当前阵容缺哪种能力
```

### 6.2 球员战术标签

每名球员增加一组战术标签或能力维度：

| 标签 | 含义 | 主要影响 |
| --- | --- | --- |
| `spacing` | 外线空间 | 外线火力、破联防、弱侧惩罚 |
| `handler` | 持球/破压迫 | 抗紧逼、团队传导、减少失误 |
| `rimPressure` | 冲框压力 | 强打内线、造犯规、压缩防线 |
| `screen` | 掩护质量 | 巨星单打、半场阵地、错位创造 |
| `poaDefense` | 持球点防守 | 防单打、防快攻发起 |
| `rimProtect` | 护框 | 收缩护框、限制冲框 |
| `rebound` | 篮板 | 终结防守、二次进攻 |
| `switch` | 换防能力 | 换防一体、防外线 |
| `pace` | 转换速度 | 提速快攻、回防速度 |
| `closer` | 关键球 | 末节关键回合稳定性 |

这些标签不一定要做成复杂 UI，但必须参与系统判断。

### 6.3 场上阵容画像

根据场上五人实时生成 `LineupProfile`。

示例：

```js
{
  team: "knicks",
  spacing: 78,
  handling: 64,
  rimPressure: 55,
  pointOfAttackDefense: 71,
  rimProtection: 48,
  rebounding: 62,
  switchability: 70,
  pace: 66,
  averageStamina: 58,
  tags: ["good_spacing", "weak_rim_protection", "handler_fatigue"]
}
```

玩家不需要看到所有数值，但系统可以展示一句清晰提示：

```text
当前阵容：空间强、护框弱、持球压力偏大。
```

### 6.4 换人建议变成“战术目的”

旧建议：

```text
布伦森体力偏低，建议换人。
```

新建议：

```text
马刺正在紧逼，布伦森体力偏低。建议补一个持球点，否则推进失误风险会继续升高。
```

旧建议：

```text
某某状态低迷，可以换下。
```

新建议：

```text
如果继续打外线火力，建议换上麦克布莱德增加弱侧投射；否则马刺会继续收缩禁区。
```

换人系统要回答：换这个人，是为了解决什么战术问题。

## 7. 战术与换人的耦合规则

每套战术应该绑定一个“理想阵容画像”。

示例：

| 战术 | 需要的阵容能力 | 缺失时反馈 |
| --- | --- | --- |
| 外线火力 | `spacing`、`handler` | 空间不足，三分战术打不出来 |
| 强打内线 | `rimPressure`、`screen`、`rebound` | 冲框受阻，容易被护框限制 |
| 提速快攻 | `pace`、`stamina`、`handler` | 提速后失误增加，体力下降 |
| 巨星单打 | `closer`、核心体力、空间 | 被包夹后弱侧惩罚不足 |
| 团队传导 | `handler`、`spacing`、多点传球 | 被紧逼压住出球 |
| 全场紧逼 | `poaDefense`、`pace`、`stamina` | 消耗过大，被打身后 |
| 包夹核心 | `switch`、轮转、弱侧防守 | 放空射手，被外线惩罚 |
| 收缩护框 | `rimProtect`、`rebound` | 放出三分空间 |

战术效果应该按三档呈现：

```text
战术克制 + 阵容适配：完整生效
战术克制 + 阵容不适配：思路正确但效果打折
战术被克制 + 阵容不适配：明显失败
```

文字直播必须把这三档说出来。

示例：

```text
完整生效：
尼克斯这次暂停调整很清楚，换上第二射手后，外线火力终于把马刺联防拉开了。
```

```text
效果打折：
战术选择没有问题，但场上少一个稳定空间点，马刺仍然敢堵在禁区。
```

```text
明显失败：
尼克斯还在强打内线，但马刺已经收缩护框，连续两个回合都被迫在身体对抗里出手。
```

## 8. 文字直播系统改造

### 8.1 三层直播结构

文字直播不应只播结果，而要承担反馈职责。

每条关键直播分三层：

```text
结果层：发生了什么
原因层：为什么发生
教练层：这和玩家调整有什么关系
```

示例：

```text
结果层：
布里奇斯底角三分命中。

原因层：
马刺联防收得太深，弱侧底角被完全放空。

教练层：
暂停后换上的射手开始产生价值，尼克斯终于用空间惩罚了收缩。
```

合成后：

```text
布里奇斯底角三分命中！马刺联防收得太深，弱侧被完全放空；暂停后换上的射手开始产生价值，尼克斯终于用空间惩罚了收缩。
```

### 8.2 直播模板按原因分类

直播模板不再只按事件分类：

```text
make
miss
turnover
block
foul
```

还要按原因分类：

```text
scheme_counter
lineup_fit
lineup_mismatch
fatigue
hot_hand
cold_hand
opponent_adjustment
coach_adjustment_success
coach_adjustment_failed
```

示例：

```text
scheme_counter：
这次不是单纯投进了，而是战术关系打出来了：{OFF_SCHEME} 正好撬开了 {DEF_SCHEME}。
```

```text
lineup_mismatch：
问题还是在人上，{PLAYER} 的能力不适合这套打法，战术执行到最后一步变形了。
```

```text
fatigue：
{PLAYER} 前面的消耗太大，这次出手短了半截，体力已经开始影响终结质量。
```

### 8.3 关键反馈优先级

每回合可能有很多原因，但直播不能太啰嗦。

建议优先级：

```text
玩家刚做过的调整
战术克制或被克制
阵容适配或不适配
体力红线
手感冷热
普通结果
```

也就是说，只要玩家刚刚换人或变阵，接下来几个回合的直播要优先回应这件事。

## 9. 调整反馈窗口

### 9.1 概念

每当玩家进行以下操作时，开启一个 `AdjustmentWindow`：

- 切换进攻战术
- 切换防守战术
- 完成换人
- 叫暂停
- 关键回合选择

窗口持续 3-5 个回合。

### 9.2 记录内容

窗口内记录：

```js
{
  type: "scheme_off",
  label: "外线火力",
  startTick: 42,
  duration: 5,
  targetProblem: "opponent_zone",
  expectedTags: ["open_three", "spacing"],
  results: {
    goodShots: 2,
    badShots: 1,
    turnovers: 0,
    pointsFor: 5,
    pointsAgainst: 2,
    fatigueImproved: false,
    lineupFitImproved: true
  }
}
```

### 9.3 反馈类型

窗口结束后给出三类反馈。

成功：

```text
这次调整很明确：尼克斯暂停后连续三回合都把球送到弱侧空位，马刺联防被打松了。
```

部分成功：

```text
换上射手后空间变好了，但布伦森体力已经偏低，最后一步终结质量还是不稳。
```

失败：

```text
这次变阵没解决根本问题，尼克斯仍然缺少第二持球点，马刺紧逼继续压住推进。
```

### 9.4 玩家学习价值

调整反馈窗口的意义是让玩家知道：

```text
我刚才的操作有没有影响比赛
影响的是哪一部分
下一步应该继续坚持，还是再次调整
```

这是建立系统感的关键。

## 10. 对手 AI 调整

### 10.1 对手需要读玩家

如果玩家连续使用同一套路，对手应该逐渐反制。

系统记录玩家倾向：

```js
{
  repeatedOffScheme: "perimeter",
  repeatedDefScheme: "zone",
  starUsageRate: 0.42,
  lowSubstitutionFrequency: true,
  tiredPrimaryHandler: true,
  overusedLineup: true
}
```

### 10.2 对手反制规则

示例：

| 玩家倾向 | 对手反制 |
| --- | --- |
| 连续外线火力 | 改换防一体，提前扑底角 |
| 连续巨星单打 | 包夹核心，逼弱侧处理 |
| 连续团队传导 | 全场紧逼，压出球点 |
| 长时间不换人 | 提速消耗，攻击疲劳点 |
| 核心体力低 | 加压持球点，逼失误 |
| 一直收缩防守 | 增加外线出手 |

### 10.3 反制必须被播出来

玩家需要知道对手不是随机变阵。

示例：

```text
马刺已经开始提前扑底角，尼克斯不能一直靠同一套外线站位吃饭。
```

```text
波波维奇明显看到了布伦森体力下降，马刺开始从后场就压他的第一下运球。
```

这会形成二阶循环：

```text
我克制你
你开始反制我
我必须换招或换人
```

## 11. UI 与信息呈现

### 11.1 指挥台改造方向

指挥台不应该只是按钮集合，而应该成为“读局面板”。

建议增加四块信息：

```text
当前战术关系
当前阵容适配
当前主要风险
建议行动
```

示例：

```text
当前战术关系：
我方外线火力 vs 对方联防，进攻占优。

阵容适配：
空间一般，持球压力偏大。

主要风险：
布伦森体力偏低，对手可能继续紧逼。

建议行动：
如果继续打外线，建议补一个射手或第二持球点。
```

### 11.2 换人界面改造方向

每个球员卡片除了体力、得分，还应显示战术标签。

示例：

```text
麦克布莱德
体力 88
标签：空间 / 持球 / 外线防守
推荐：破联防、抗紧逼
```

```text
阿丘瓦
体力 76
标签：篮板 / 护框 / 活力
推荐：保护禁区、终结防守回合
```

### 11.3 信息量控制

不要把所有数值暴露给玩家。

推荐展示方式：

```text
强 / 一般 / 弱
适配 / 勉强 / 不适配
建议 / 风险 / 已见效
```

这样既保留系统深度，又不把界面做成表格模拟器。

## 12. 典型完整案例

### 12.1 破联防案例

局势：

```text
马刺改打联防，尼克斯连续两次冲框受阻。
```

系统提示：

```text
对手收缩明显，外线空间可能是突破口。
```

玩家操作：

```text
切换进攻战术：外线火力。
```

如果没换人：

```text
战术思路是对的，但场上空间点不够，马刺仍然敢堵在禁区。
```

玩家暂停并换上射手。

后续直播：

```text
麦克布莱德上来后弱侧被拉开，马刺联防第一次被迫横移。布里奇斯底角接球，三分命中。
```

调整反馈：

```text
这次调整开始见效：尼克斯用第二射手把联防拉开，连续两个回合获得外线空位。
```

### 12.2 抗紧逼案例

局势：

```text
马刺全场紧逼，尼克斯连续两个回合推进困难。
```

系统提示：

```text
对手正在压持球点，单靠布伦森推进风险越来越高。
```

玩家操作：

```text
换上第二持球点，战术改为团队传导。
```

后续直播：

```text
这次尼克斯没有让布伦森一个人硬扛，第二持球点提前接应，马刺的第一波紧逼被拆掉了。
```

调整反馈：

```text
换人解决了推进问题，尼克斯过去三个回合没有再被紧逼直接逼出失误。
```

### 12.3 核心疲劳案例

局势：

```text
布伦森体力低，但玩家继续巨星单打。
```

后续直播：

```text
布伦森还是想自己解决，但这次急停明显短了，前面连续持球的消耗已经影响到腿。
```

系统建议：

```text
如果继续围绕布伦森，建议叫暂停回体力；否则需要换打法，让弱侧分担处理球。
```

玩家如果忽视：

```text
马刺看准了布伦森体力下降，开始提前夹击他的第一下启动。
```

## 13. 分阶段落地计划

### 第一阶段：建立因果层

目标：

```text
先让系统知道每回合为什么发生。
```

内容：

- 新增 `PossessionContext`。
- 新增基础原因标签。
- 回合结算时记录战术克制、阵容适配、疲劳、手感等因素。
- 文字直播优先读取原因标签。

交付标准：

```text
关键回合能说出“为什么”，而不只是“发生了什么”。
```

### 第二阶段：阵容画像与球员标签

目标：

```text
让换人和战术产生明确关系。
```

内容：

- 为球员增加战术标签。
- 新增 `LineupProfile`。
- 每套战术绑定理想阵容需求。
- 换人建议从“体力建议”升级为“战术建议”。

交付标准：

```text
换人建议必须说明战术目的。
```

### 第三阶段：调整反馈窗口

目标：

```text
让玩家知道刚才的操作是否奏效。
```

内容：

- 新增 `AdjustmentWindow`。
- 玩家变阵、换人、暂停后追踪 3-5 回合。
- 根据窗口结果生成成功、失败、部分成功反馈。

交付标准：

```text
玩家操作后 3-5 回合内必须出现一次明确反馈。
```

### 第四阶段：对手读玩家

目标：

```text
让比赛形成动态博弈，而不是固定最优解。
```

内容：

- 记录玩家战术倾向。
- 对手根据倾向反制。
- 反制行为进入文字直播。

交付标准：

```text
玩家重复使用同一策略时，对手会有可感知的针对性调整。
```

### 第五阶段：指挥台信息重构

目标：

```text
让玩家更容易读懂局势。
```

内容：

- 展示当前战术关系。
- 展示阵容适配。
- 展示主要风险。
- 展示建议行动。

交付标准：

```text
玩家进入指挥台后，能在 5 秒内知道当前最大问题是什么。
```

## 14. 验收标准

### 14.1 玩家体验标准

玩家应该能自然说出：

```text
我为什么要换这个人。
我为什么要切这个战术。
这次调整为什么成功。
这次调整为什么失败。
对手下一步可能怎么反制。
```

### 14.2 系统可验证标准

每个关键回合至少能追溯到一个原因：

```text
战术克制
战术被克制
阵容适配
阵容不适配
体力问题
手感问题
对手反制
玩家调整生效
玩家调整失败
```

### 14.3 文本标准

关键文字直播至少满足一个条件：

- 解释战术关系。
- 解释换人效果。
- 解释体力或状态影响。
- 解释对手反制。
- 回应玩家最近一次操作。

### 14.4 UI 标准

指挥台至少能回答：

```text
现在我被什么限制？
现在我的战术是否克制对手？
当前阵容能不能执行这个战术？
下一步最合理的调整是什么？
```

## 15. 风险与注意事项

### 15.1 不要先加更多战术按钮

当前问题不是战术数量不足，而是战术、换人、直播之间的因果回声不足。

在因果层没有建立前，增加更多战术只会让系统更散。

### 15.2 不要把所有数值暴露给玩家

玩家需要的是判断依据，不是完整公式。

推荐表达：

```text
空间强
持球偏弱
护框不足
战术适配
效果打折
```

不推荐表达：

```text
spacing = 78
handler = 61
matchupMod = 0.043
```

### 15.3 文字反馈不能过度刷屏

每个回合只突出一个主要原因。

优先级：

```text
玩家最近操作 > 战术克制 > 阵容适配 > 体力风险 > 普通结果
```

### 15.4 对手反制要有预兆

对手不能突然无理由变强。

要先通过文字直播告诉玩家：

```text
对手开始提前扑外线。
对手开始压持球点。
对手开始攻击疲劳球员。
```

玩家看到预兆后，再被反制，才会觉得公平。

## 16. 总结

这套改造的本质，是把战术、换人、文字直播从三个并列模块，变成一个共享因果链的教练系统。

最终结构应该是：

```text
战术提出意图
换人提供执行资源
回合结算验证效果
文字直播解释原因
对手 AI 制造新问题
玩家继续调整
```

一句话目标：

```text
让玩家感觉每一次战术和换人都不是孤立操作，而是在一场会回应、会反制、会讲清楚原因的比赛里执教。
```

## 17. 可行性分析

### 17.1 总体现状判断

这套方案整体可行，而且适合在当前项目上分阶段演进。

原因是当前代码已经具备几个关键地基：

- 已有球员基础能力：`off`、`thr`、`def`、`reb`、`pg`、`ft`、`star`。
- 已有战术数据：`OFF_SCHEMES`、`DEF_SCHEMES`、`MATCHUP`、`DEF_BASE`。
- 已有状态系统：体力、手感、气势、比分、回合、场上阵容、当前战术都已经存在。
- 已有教练反馈雏形：`coachPrompt`、`pendingCoachEffect`、`coachStats`、`targetLevel`。
- 已有文字直播模板：按事件类型生成文本，具备扩展成原因模板的基础。
- 已有 AI 原生验证：后续新增状态和 UI 可以纳入验证契约。

当前主要缺口不是“系统从零开始”，而是缺少一个统一的因果层，把已有数值和文本组织成玩家能理解的反馈。

## 18. 分点可行性详析

### 18.1 `PossessionContext`：高可行性，建议最先做

当前回合核心逻辑集中在 `runPossession()`，这对接入因果上下文很有利。

可行做法：

```text
1. 在回合开始创建 context。
2. 战术、体力、手感、对手防守等因素只往 context 写标签。
3. 回合结束时，把 outcome 和主要原因写入 context。
4. 文字直播读取 context 生成解释。
```

第一版不需要改变所有数值算法，只需要把现有判断结果记录下来。

示例：

```js
context.causes.push("off_scheme_counters_def");
context.causes.push("primary_handler_tired");
context.outcomeTags.push("miss_short");
```

可行性高的原因：

- 不需要新增 UI。
- 不需要先改所有战术。
- 不需要改变玩家操作流程。
- 可以逐步让文本和验证系统读取它。

主要风险：

- 如果一开始就把数值和文本全绑死，会让 `runPossession()` 更复杂。
- 应该先做“记录原因”，再做“原因影响结果”，最后再做“原因驱动文本”。

建议第一阶段只做轻量结构：

```text
primaryCause
secondaryCause
outcomeTags
coachRelevant
```

### 18.2 `LineupProfile`：高可行性，但需要先推导后手工校准

当前球员已经有基础属性：

```text
off
thr
def
reb
pg
ft
star
stamina
heat
```

这些足够推导第一版阵容画像。

例如：

```text
spacing      可以由 thr + off 推导
handling     可以由 pg + off 推导
rimPressure  可以由 off、pos、star 推导
poaDefense   可以由 def + pos 推导
rimProtect   可以由 def + reb + pos 推导
rebounding   直接由 reb 推导
pace         可以先由 pos + pg + def 粗略推导
closer       可以由 star + CLUTCH_MAP 推导
```

第一版可以不新增球员数据，先通过函数计算。

后续再补显式标签：

```js
traits: ["spacing", "handler", "poaDefense"]
```

主要风险：

- 纯推导会比较粗，比如 `thr` 高不一定等于“战术级空间点”。
- 有些球员真实定位需要策划判断，不能完全依赖数字。

建议：

```text
第一版：用现有属性推导。
第二版：给核心轮换手工补标签。
第三版：根据 playtest 调整标签权重。
```

### 18.3 球员战术标签：中可行性，资源缺口较明显

球员标签是换人系统变得“有战术目的”的关键。

但这是目前资源缺口最大的部分之一。

当前已有：

- 球员名单。
- 基础能力值。
- 部分球员风格数据。
- 轮换时间目标。

缺少：

- 每名球员的显式战术标签。
- 每个标签的设计定义。
- 标签和战术之间的对应权重。
- 标签是否展示给玩家的 UI 规则。

建议先做最小标签集，不要一口气做十几个。

第一版推荐只做 6 个：

```text
spacing
handler
rimPressure
poaDefense
rimProtect
rebound
```

这 6 个足以支撑大多数战术和换人反馈。

后续再加：

```text
switch
pace
screen
closer
```

### 18.4 战术执行质量：高可行性，但需要谨慎调参

当前已有战术克制表 `MATCHUP`，可以继续保留。

新的执行质量不是替代 `MATCHUP`，而是叠加一个“能不能执行”的判断。

推荐公式结构：

```text
finalSchemeImpact =
  matchupImpact
  * lineupFitMultiplier
  * staminaExecutionMultiplier
  * opponentAdaptationMultiplier
```

不要一开始增加太多加减项，否则很难平衡。

第一版建议只做三档：

```text
适配：完整收益
勉强：收益打 60%-70%
不适配：收益打 20%-40%，并生成失败反馈
```

可行性高的原因：

- 战术种类已经稳定。
- 阵容画像可以提供适配判断。
- 文字直播可以直接解释适配状态。

主要风险：

- 如果惩罚太重，玩家会被迫每套战术都换固定人。
- 如果惩罚太轻，阵容适配又没有存在感。

建议把第一版影响控制在“可感知但不决定一切”的范围。

### 18.5 换人战术建议：高可行性，收益很快

这是最值得早做的体验提升点。

当前换人界面已经有：

- 场上球员。
- 替补球员。
- 体力条。
- 状态标签。
- `getSubSuggestion()`。

只要换人建议从“体力建议”变成“战术目的建议”，玩家感受会立刻变好。

示例：

```text
当前：布伦森体力偏低，建议轮换。

改造后：马刺正在紧逼，布伦森体力偏低。建议补一个持球点，否则推进失误风险会继续升高。
```

可行性高的原因：

- 不必先改回合算法。
- 不必新增复杂 UI。
- 可以直接复用当前 `coach-advice` 和 `sub-advice` 区域。

主要风险：

- 如果建议只说“上 A 下 B”，会变成自动答案，降低玩家判断空间。

建议表达成：

```text
问题 + 需求 + 候选方向
```

不要表达成：

```text
唯一正确答案
```

### 18.6 原因型文字直播：中高可行性，文案资源是主要成本

当前直播已经有大量模板，系统也有 `pushFeed()` 和 `maybeRichFeed()`。

技术上可行，但内容资源要求高。

原因型直播需要新增模板类别：

```text
scheme_counter
scheme_blocked
lineup_fit
lineup_mismatch
fatigue_effect
hot_hand_effect
opponent_adjusted
coach_adjustment_success
coach_adjustment_failed
```

第一版不需要每类很多条。

建议最低配置：

```text
每类 4-6 条
总量约 40-60 条
```

这样能避免高频重复。

主要风险：

- 文本过长会打断比赛节奏。
- 解释太频繁会像系统教程，不像直播。

建议：

```text
普通回合仍保持短。
玩家刚调整后的 3-5 回合才提高解释密度。
关键回合优先解释。
```

### 18.7 调整反馈窗口：中高可行性，设计难点在判定标准

当前已有 `pendingCoachEffect`，可以视为这个系统的雏形。

可行做法：

```text
玩家操作后创建 adjustmentWindow。
接下来 3-5 回合收集 context。
窗口结束后输出一条总结反馈。
```

第一版只记录少量指标：

```text
pointsFor
pointsAgainst
goodShotCount
turnoverCount
matchedCauseCount
lineupFitChanged
```

判定标准可以先简单：

```text
成功：目标原因出现 2 次以上，且净效果不差。
部分成功：目标原因出现，但被体力/手感/对手反制抵消。
失败：目标原因没出现，或连续产生负面标签。
```

主要风险：

- 如果成功/失败判断过于机械，会和玩家观感冲突。
- 例如投丢了空位球，战术其实成功，但比分没体现。

所以反馈标准要优先看“过程质量”，不是只看得分。

### 18.8 对手读玩家：中可行性，必须有公平预告

当前已有 `aiThink()` 和 `targetLevel`，说明项目已经有“对手针对玩家”的雏形。

可行方向：

```text
记录玩家最近 N 回合战术倾向。
如果重复度过高，对手逐步提高反制概率。
反制前先播预兆文本。
```

不建议一开始做复杂 AI。

第一版只做 4 种倾向：

```text
连续外线
连续单打
连续不换人导致疲劳
连续同一防守
```

对应反制：

```text
外线 -> 换防/扑射手
单打 -> 包夹核心
疲劳 -> 提速或紧逼
同一防守 -> 改进攻方向
```

主要风险：

- 玩家如果没看到预兆，会觉得系统突然作弊。
- 对手反制太快，会压缩玩家享受调整成功的时间。

建议节奏：

```text
玩家连续 3-4 次同倾向 -> 文字预兆
再过 1-2 回合 -> 对手实际反制
```

### 18.9 指挥台信息重构：中可行性，UI 空间是限制

现有指挥台已经有战术按钮、换人区、建议区。

可行，但要克制信息量。

建议新增的不是大面板，而是一个小型“读局摘要”：

```text
战术关系：外线火力克制联防
阵容适配：空间一般，持球偏弱
主要风险：布伦森体力下降
建议方向：补持球点或降低单打频率
```

风险：

- 手机屏幕空间有限。
- 如果一次显示太多，玩家不会读。
- 如果强行显示数值，会破坏直播游戏的氛围。

建议：

```text
默认显示一句总评。
展开后显示 3-4 行细节。
不要展示具体公式。
```

### 18.10 AI 原生验证扩展：高可行性，应伴随系统同步更新

当前已经有 `src/ai-verify.mjs`、`AI_VERIFY_CONTRACT`、JSON 快照和稳定 `data-testid`。

后续新增系统时，建议同步把以下字段加入验证快照：

```text
lastPossessionContext
lineupProfile
activeAdjustmentWindow
opponentAdaptation
coachFeedbackSummary
```

这样 AI 可以验证：

```text
玩家操作后是否创建反馈窗口
阵容画像是否变化
文字直播是否回应了最近调整
对手是否因为玩家重复行为而反制
```

风险：

- 快照字段如果频繁改名，会影响后续自动验证。

建议：

```text
先定义字段名。
允许字段值逐步丰富。
不要频繁破坏结构。
```

## 19. 资源缺口清单

### 19.1 球员战术标签数据

缺口：

```text
每名球员的 spacing、handler、rimPressure、poaDefense、rimProtect、rebound 等标签。
```

当前可以用基础属性推导，但最终最好手工校准。

影响：

```text
没有标签，换人建议会比较泛。
没有标签，阵容适配只能粗略判断。
```

建议补充形式：

```js
traits: {
  spacing: 82,
  handler: 76,
  rimPressure: 68,
  poaDefense: 72,
  rimProtect: 20,
  rebound: 35
}
```

### 19.2 原因型文字模板

缺口：

```text
战术克制、阵容适配、换人见效、调整失败、对手反制等原因模板。
```

影响：

```text
没有模板，系统就算知道原因，也很难让玩家感受到。
```

最低需求：

```text
每类原因 4-6 条。
第一批约 40-60 条。
```

### 19.3 战术适配规则表

缺口：

```text
每套战术需要哪些阵容能力，以及缺失时如何打折。
```

影响：

```text
没有规则表，战术和换人仍然无法稳定关联。
```

建议补充：

```text
外线火力 -> spacing、handler
强打内线 -> rimPressure、screen、rebound
全场紧逼 -> poaDefense、pace、stamina
包夹核心 -> switch、rotation、weaksideDefense
```

### 19.4 调整反馈判定标准

缺口：

```text
什么叫一次调整成功、部分成功、失败。
```

影响：

```text
没有标准，反馈窗口只能写死文案，无法可信地总结比赛。
```

建议先定义轻量标准：

```text
过程质量优先于比分。
空位机会、失误减少、阵容适配改善，都可以算成功信号。
```

### 19.5 对手反制节奏表

缺口：

```text
玩家重复几次后，对手多久预告，多久执行反制。
```

影响：

```text
没有节奏表，对手 AI 容易显得随机或作弊。
```

建议：

```text
连续 3-4 次同倾向 -> 预兆。
再 1-2 回合 -> 反制。
反制持续 3-5 回合，之后重新评估。
```

### 19.6 指挥台 UI 草图

缺口：

```text
读局摘要、阵容适配、风险提示在手机界面中的排布方案。
```

影响：

```text
如果没有 UI 草图，执行时容易把信息堆得太满。
```

建议先做低保真：

```text
一行总评 + 三行详情 + 一个建议方向。
```

### 19.7 调参目标与测试样本

缺口：

```text
各类战术调整应该带来多大影响。
不同玩家操作路径下，比赛结果是否合理。
```

影响：

```text
没有调参目标，系统可能变成“点对按钮就赢”或“怎么调都没用”。
```

建议准备：

```text
3 条标准测试脚本：
破联防脚本
抗紧逼脚本
核心疲劳脚本
```

每条脚本验证：

```text
正确调整有感。
错误调整有代价。
不调整会被针对。
```

### 19.8 自动验证用例

缺口：

```text
针对新系统的 AI 可验证断言。
```

影响：

```text
改动变大后，容易出现 UI 有文本但状态没同步，或状态有原因但直播没反馈。
```

建议新增断言：

```text
战术切换后创建 adjustmentWindow。
换人后 lineupProfile 发生变化。
关键直播包含 context cause。
对手反制时 opponentAdaptation 不为空。
```

### 19.9 文案风格约束

缺口：

```text
原因型直播的长度、语气、重复限制。
```

影响：

```text
没有约束，新增文案可能像系统说明，不像直播。
```

建议：

```text
普通回合 1 句话。
关键反馈最多 2 句话。
每 3-5 回合最多 1 条长解释。
```

## 20. 推荐执行策略

建议不要一次性做完整大系统。

最稳妥路线：

```text
第一步：PossessionContext 只记录原因，不大改数值。
第二步：LineupProfile 用现有属性推导，不立刻补全所有球员标签。
第三步：换人建议先战术化，最快提升玩家感受。
第四步：直播模板补第一批原因文案。
第五步：加入 adjustmentWindow，总结玩家调整。
第六步：再做对手反制和 UI 重构。
```

每一步都应该可单独验证、可单独回滚。

优先级建议：

```text
P0：PossessionContext、LineupProfile 基础版。
P1：换人战术建议、原因型直播第一批、AI 验证字段。
P2：AdjustmentWindow、对手读玩家、指挥台读局摘要。
P3：完整球员标签校准、更多文案、复杂反制策略。
```

这套执行策略的好处是：

```text
先建立因果语言。
再让换人和战术读同一套原因。
最后才增加复杂 AI 和 UI。
```
